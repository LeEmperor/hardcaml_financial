# Xilinx synthesis reports

`xilinx_reports.exe` uses
[`hardcaml_xilinx_reports`](https://github.com/janestreet/hardcaml_xilinx_reports) to
generate out-of-context Vivado projects and summarize timing and primitive utilization.
It is separate from `lib/common/generate.exe`: the reports library emits its own Verilog,
clock XDC, Tcl, and report artifacts for each selected circuit.

The available targets are:

| Target | Hardcaml circuit | Clock port |
| --- | --- | --- |
| `uart-tx` | `Uart_tx` | `clk` |
| `uart-rx` | `Uart_rx` | `clock` |
| `cme-feed-parser` | `Cme_feed_parser` | `clk` |
| `uart-frame-parser` | `Uart_frame_parser` | `clock` |
| `uart-loopback-harness` | `Uart_loopback_validation_harness` | `clk100mhz` |

The clock column is not decoration: `-clock` names an actual top-level port, and the
ports are not named consistently across these blocks yet — that is the `_i` / `_o` rename
the formatting guide asks for and `lib/` has not had. Read the column, do not guess.

## Inspect or generate a project

Show the available targets and the flags generated by the reports library:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- -help
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- uart-tx -help
```

Generate a project without launching Vivado:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- uart-tx \
  -dir _build/xilinx-reports/dry-run \
  -part xc7a100tcsg324-1 \
  -clock clk:100
```

Generated files are written below a circuit-named subdirectory, such as
`_build/xilinx-reports/dry-run/uart_tx/`. They remain untracked because `_build/` is
ignored.

Standard Vivado utilization and timing reports are always enabled by this wrapper. The
upstream `-reports` flag remains visible for compatibility, but it is not necessary.

After Vivado finishes, the command prints a curated utilization table, the Vivado setup,
hold, and pulse-width summary, and the paths of all report artifacts. Add `-full-report`
to print the complete standard utilization and timing reports directly to the terminal.

The compact report contains timing data, but its upstream primitive-group queries are
designed for UltraScale devices and return zero utilization on `xc7a100t`. To avoid
displaying a convincing but incorrect zero table, this executable disables the compact
primitive groups. The generated standard `post_synth_<circuit>.utilization` file is the
authoritative resource report.

## Run report profiles

Timing-oriented profile, including the design hierarchy below the selected circuit:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- uart-tx \
  -dir _build/xilinx-reports/timing/uart-tx \
  -part xc7a100tcsg324-1 \
  -clock clk:100 \
  -hierarchy \
  -full-design-hierarchy true \
  -jobs 1 \
  -run
```

Resource-oriented profile, black-boxing any child circuits while each circuit is
synthesized independently:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- uart-rx \
  -dir _build/xilinx-reports/resources/uart-rx \
  -part xc7a100tcsg324-1 \
  -clock clock:100 \
  -hierarchy \
  -full-design-hierarchy false \
  -jobs 1 \
  -run
```

The board harness is the one target worth running at the real system clock, because it is
the only one whose clock is a physical pin:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- uart-loopback-harness \
  -dir _build/xilinx-reports/timing/uart-loopback-harness \
  -part xc7a100tcsg324-1 \
  -clock clk100mhz:100 \
  -hierarchy \
  -full-design-hierarchy true \
  -jobs 1 \
  -run
```

`-hierarchy` creates a report project for the selected top and every circuit recorded in
its Hardcaml circuit database. Note that nothing in this repository currently creates a
hierarchy boundary — every block is a plain `create scope` call rather than a
`Hierarchy.In_scope` instantiation, so the database comes back empty and `-hierarchy` has
one project to make. `test/validation/board_hierarchy/` asserts that, so the day it stops
being true a test says so. `-full-design-hierarchy true` includes child implementations in
each project; `false` emits them as black boxes for local resource attribution.

The default profile leaves Vivado free to flatten and optimize across RTL boundaries. Use
`-dont-flatten-hierarchy` only for an explicit attribution or debug experiment, keep its
output in a separate directory, and compare its top-level timing and area with the ordinary
run. It is not the default timing or signoff profile.

To include the complete reports in terminal output, add:

```text
-full-report
```

Vivado defaults to the executable named `vivado`. If it is not on `PATH`, add:

```text
-path-to-vivado /path/to/Vivado/bin/vivado
```

Start with one job. A single Vivado process can consume several gigabytes, while the
reports library otherwise permits several circuit projects to run concurrently.

## Scope and limitations

These are out-of-context estimates. The generated XDC contains only clock declarations; it
does not include the pin, I/O delay, false-path, or asynchronous-clock-group constraints in
`validation/constraints/unified_tx_rx.xdc`.

Consequently, the single-clock block reports are the most directly comparable. The board
harness report gives aggregate resource and same-clock internal timing estimates, but it
does not replace a Vivado board project for pin timing, placement and routing signoff, DRC,
or bitstream generation.

The upstream runner represents a failed Vivado subprocess as a missing report instead of
making its generated command exit nonzero. This project wrapper compensates by requiring all
three expected report files to exist, be nonempty, and have been refreshed by the current
run before it prints a successful summary. That check is the reason a Vivado failure here
surfaces as an error rather than as last run's numbers printed again.

No run has been recorded against this repository's blocks yet. When one is, record the
toolchain it was produced with — OCaml, dune, `hardcaml`, `hardcaml_xilinx_reports`, Vivado,
and the part — the same way `scripts/generate_rtl.py` records it in `MANIFEST.txt` for the
emitted RTL. A resource number without a toolchain attached is not comparable to the next
one.
